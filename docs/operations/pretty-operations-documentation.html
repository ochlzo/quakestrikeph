Getting started

Choose the task you need. You can read the Docker explanations later.

Where should I start?
Your task Go to
I already set up this computer. Start the local Bulletin app.
This is my first time on this computer. Set up local development.
I need new earthquake data or forecasts. Run the workers.
I need to update the live website. Follow the production procedure.

For local commands: Start Docker Desktop. Open PowerShell in the repository folder.

Use the repository folder 
Set-Location C:\Projects\quakestrikeph\redo\quakestrikeph

File links open VS Code. Set your repository folder if needed.

Keep .env private. Run each command separately. If a command fails, fix the error before continuing.

Check that Docker is ready
Check Docker and Compose 
docker info --format "{{.ServerVersion}}"
docker compose version

Check: Both commands print a version. If Docker cannot connect, open Docker Desktop and wait for its engine to start.

Run the Bulletin locally

Use this when you want to edit or check the Bulletin on your computer. Complete first-time setup once before using these commands.

  1. Start the application.

    PowerShell · Start local web services 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml up -d --wait postgres redis backend-api bulletin

  2. Check the containers.

    Check local status 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml ps postgres redis backend-api bulletin

    Check: All four services show as running and healthy. If one is unhealthy, read its logs below.

  3. Open the Bulletin.

    Open http://127.0.0.1:4321. Save a Bulletin source file to see your changes.

Which services start with Bulletin?

While you work

Read the Bulletin and Backend logs
Follow logs 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml logs -f --tail 100 bulletin backend-api

Press Ctrl + C to leave the log view. The containers keep running.

Apply Backend code changes

Backend source is copied into its image. Rebuild and recreate the Backend after changing its code.

Rebuild only Backend 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml build backend-api
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml up -d --wait --no-deps backend-api

Check: Backend becomes healthy. Bulletin requests now reach the rebuilt Backend.

After changing Bulletin dependencies

If the Bulletin lockfile changes, rebuild its image and replace its dependency volume.

Refresh Bulletin dependencies 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml build bulletin
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml up -d --wait --no-deps --force-recreate -V bulletin

-V refreshes the Bulletin container’s anonymous volume. This command does not replace the PostgreSQL or Redis volumes.

When you finish

Stop only the web apps 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml stop bulletin backend-api

PostgreSQL, Redis, and any running workers stay available. Use the startup command above when you return.

Do not use down just to stop Bulletin. The web apps and workers share PostgreSQL and Redis.

Work on Backend without Bulletin
Start Backend and its data services 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml up -d --wait postgres redis backend-api

Backend listens at http://127.0.0.1:3000. To stop only Backend, use:

Stop only Backend 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml stop backend-api

First-time local setup

Use this for a new local database. You do not repeat these steps every day.

If the database already contains data, back it up first. Stop its producers and consumers before migrations. Follow the local runtime guide for that shared database.

  1. Prepare the tools and model package.

    Install Docker Desktop, Git, Python 3.12, and uv. Get the approved model package from the maintainer.

    Web-only work does not require the history import or running workers.

  2. Create your local configuration.

    If .env does not exist, copy the example. Keep an existing .env.

    Create .env only if it is missing 
    if (-not (Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }

    Edit .env using the settings below. The example values are placeholders.

    Settings to prepare before continuing
    Setting What to enter
    Database passwords Add distinct POSTGRES_PASSWORD, MIGRATION_DB_PASSWORD, WORKER_DB_PASSWORD, and BACKEND_DB_PASSWORD.
    Database URLs Match each password to its login in MIGRATION_DATABASE_URL, DATABASE_URL, and BACKEND_DATABASE_URL. Keep the host as postgres.
    Model Set MODEL_RELEASE_ID from the approved manifest. Point MODEL_ARTIFACT_HOST_DIRECTORY at the packaged model.
    Web and accounts Set the Clerk keys, authorized local URLs, ACCOUNT_REDIS_URL, and account provider settings from the local runtime guide.
    Other required values Set the official PHIVOLCS_CATALOG_URL and a nonempty BACKEND_IMAGE_TAG. Local builds use :local images.
    See the exact web settings

    Set CLERK_SECRET_KEY, CLERK_PUBLISHABLE_KEY, PUBLIC_CLERK_PUBLISHABLE_KEY, and IPROG_API_TOKEN for account features. Set CLERK_AUTHORIZED_PARTIES=http://localhost:4321,http://127.0.0.1:4321 and ACCOUNT_REDIS_URL=redis://redis:6379/0. Follow section 9 of the local runtime guide for setup details.

  3. Package the approved model.

    Replace the example path with the approved package folder. Run each command separately.

    Prepare Python and package the model 
    uv python install 3.12
uv sync --project workers --frozen
$sourcePackage = 'C:\path\to\reviewed-model-package'
uv run --project workers quakestrike package-model-release --source-package $sourcePackage

    Check: Model packaging succeeds. Its release ID matches MODEL_RELEASE_ID in .env.

  4. Start PostgreSQL and Redis.

    Start the data services 
    docker compose --env-file .env -f infrastructure/compose.yml up -d --wait postgres redis

    Check: Both containers become healthy.

  5. Create the database logins.

    Create migration and worker roles 
    docker compose --env-file .env -f infrastructure/compose.yml exec -T postgres sh /opt/quakestrike/provision-roles.sh create

  6. Apply the database migrations.

    Migrations create or update database tables. Starting containers does not run migrations.

    Build and run the one-time setup container 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml run --build --rm local-init

  7. Register and verify the model.

    Register, then verify 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml run --rm local-init quakestrike register-model-release
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml run --rm local-init quakestrike verify-model-release

  8. Create the Backend database login.

    Grant Backend its access 
    docker compose --env-file .env -f infrastructure/compose.yml exec -T postgres sh /opt/quakestrike/provision-roles.sh create-backend

  9. Build the web images.

    Build Backend and Bulletin 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml build backend-api bulletin

    Continue with Run the Bulletin locally.

Check: Setup is complete when all four services are healthy and Bulletin opens. An empty event list can mean history has not been imported.

Run the workers locally

Workers fetch PHIVOLCS data and create forecasts. You can edit Bulletin without running them.

Before you start: Use initialized data, tested worker images, the approved model, and a successful history import. Keep alert delivery disabled unless the team has approved its separate activation.

First time running workers? Start here.

Use this for a new local database. Complete local setup first. Keep web apps and all workers stopped during database initialization. For an existing database, follow the runtime guide before changing it.

  1. Prepare worker settings and source history.

    Set WORKER_IMAGE_TAG to the tested full commit SHA. Keep that clean checkout available for the build scripts.

    Get a preserved PHIVOLCS snapshot from the maintainer. Set BOOTSTRAP_REQUIRED_AVAILABLE_THROUGH to its verified source coverage time.

    Replace the example path, then copy the snapshot without editing it.

    Prepare the history input 
    $snapshotPath = 'C:\path\to\preserved-bootstrap-snapshot.json'
New-Item -ItemType Directory -Force bootstrap-snapshots | Out-Null
Copy-Item -LiteralPath $snapshotPath -Destination bootstrap-snapshots/input.json

  2. Start data services and build worker images.

    Wait for each command to finish 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml up -d --wait postgres redis
& infrastructure/scripts/build-worker-image.ps1
& infrastructure/scripts/build-prediction-image.ps1

    The build scripts require the tested clean checkout and refuse to overwrite an existing release image tag. Keep an existing verified image instead of overwriting it.

  3. Prepare the worker database access.

    Provision roles, migrate, and grant access 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml exec -T postgres sh /opt/quakestrike/provision-roles.sh create
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml run --rm release-init quakestrike migrate
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml exec -T postgres sh /opt/quakestrike/provision-roles.sh grant-worker

  4. Verify the model and check old prediction work.

    Run one command at a time 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml run --rm release-init quakestrike register-model-release
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml run --rm release-init quakestrike verify-model-release
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml run --rm release-init quakestrike reissue-legacy-predictions

    Check: The reissue command prints "status": "completed". A new database has no old jobs to reissue.

  5. Import history and check readiness.

    Import, then check 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml run --rm release-init quakestrike bootstrap --snapshot /app/bootstrap-snapshots/input.json --run-manifest /app/bootstrap-snapshots/bootstrap-readiness.json
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml run --rm release-init quakestrike startup-check --run-manifest /app/bootstrap-snapshots/bootstrap-readiness.json

    Check: The final command exits successfully and prints "ready": true. Keep Beat off until this check passes.

Continue with the worker startup sequence below. See the runtime guide for snapshot requirements and existing-database recovery.

Start an initialized worker setup

  1. Start the data services.

    Start shared PostgreSQL and Redis 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml up -d --wait postgres redis

  2. Start Dispatcher and Data Ingestor.

    Wait for each command to succeed 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml up -d --wait dispatcher
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml up -d --wait data-ingestor

  3. Start Prediction Worker.

    Start prediction processing 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml --profile prediction up -d --wait prediction-worker

  4. Enable the schedule last.

    Check consumers and enable Beat 
    & infrastructure/scripts/enable-beat.ps1

    Check: The script succeeds. Beat waits for the next five-minute boundary; it does not fetch data immediately.

Check worker status 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml --profile prediction --profile beat ps dispatcher data-ingestor prediction-worker beat
Read worker logs
Follow worker logs 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml --profile prediction --profile beat logs -f --tail 100 dispatcher data-ingestor prediction-worker beat
Stop the worker setup

Stop the scheduler first. Stop Dispatcher next. Let active jobs finish before stopping consumers when possible.

Stop in order 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml --profile beat stop beat
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml stop dispatcher
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml --profile prediction stop data-ingestor prediction-worker

The database, Redis, and web apps stay running. If alert services are active, also follow their stop procedure.

How prediction and alerts follow ingestion

Data Ingestor saves event changes and prediction jobs. Dispatcher sends prediction commands through Redis. Prediction Worker saves forecasts.

When alert gates are enabled, Dispatcher also handles eligible alert work. Alert Worker sends through providers. Reconciliation and Backend callbacks record delivery evidence.

Workers do not pass full events directly to each other. PostgreSQL keeps records; Redis carries commands containing record identifiers.

Operate production

Use this section for the live VPS. Local development commands belong on your computer.

First production setup

The maintainer must prepare the VPS, private configuration, backups, model, history, and Cloudflare Tunnel before the first release.

  1. Complete VPS initialization and worker initialization.
  2. Complete Backend setup and its account configuration.
  3. Follow the first Bulletin rollout with automatic deployment disabled.
  4. Verify the public pages and API before enabling automatic deployment.

Update an existing production setup

  1. Wait for the tested main commit.

    Use the commit that passed the required main checks. When automatic deployment is enabled, successful main checks trigger deployment.

  2. If a manual rollout is required, use the deployment script.

    Run from /srv/quakestrikeph on the VPS using Bash. Replace the placeholder with the full tested main SHA.

    VPS · Bash · Manual deployment 
    cd /srv/quakestrikeph
bash infrastructure/scripts/deploy-workers.sh REPLACE_WITH_TESTED_40_CHARACTER_MAIN_SHA

  3. Check the deployment result.

    Wait for the script or CI job to finish successfully. Open the public Bulletin. Check the map, event list, and a forecast page.

    VPS · Check service status 
    docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.edge.yml -f infrastructure/compose.bulletin.yml --profile prediction --profile beat --profile alerts ps

    Only previously enabled optional services should run. Follow the deployment guide for public API and recovery checks.

Do not replace this procedure with a generic compose up. The deployment script coordinates backups, migrations, readiness checks, and recovery.

What the deployment script handles

The script builds tested images, verifies backups, stops processing, applies reviewed migrations and grants, and checks readiness.

It resumes services, preserves the prediction replica count, and restores Beat only if Beat was previously enabled. Alerts remain separately gated.

If the database schema changes and deployment fails, follow the repair-forward procedure. The script does not automatically downgrade or restore the live database.

Fix common problems

Read the error from the failed command first. Use logs to check which service needs attention.

Docker cannot connect

Open Docker Desktop. Wait for the engine to start, then run the command again.

Check the engine 
docker info --format "{{.ServerVersion}}"
Port 4321 is already in use

Stop the other Bulletin server using that port. Then repeat the local startup command. Do not start a second development server.

A container is unhealthy or keeps restarting
Check status, then recent logs 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml ps
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.backend.yml -f infrastructure/compose.local.yml logs --tail 100 backend-api bulletin

Check the named service’s error. Fix the missing setting, unavailable database, or application error before restarting it.

Compose says a variable is missing

Check that you are in the repository folder and .env exists. Set the variable named in the error.

Keep --env-file .env in the command. Do not paste private configuration or resolved passwords into a chat.

My code change does not appear

Bulletin source updates use mounted local files. Backend changes require a rebuild. Dependency changes require the Bulletin dependency refresh.

Use the matching procedure under Run the Bulletin locally.

The Bulletin is empty

Check Backend logs first. A healthy app can have no stored events. Start initialized workers or follow the history import procedure.

Do not delete the database volume to fix an empty list.

Workers do not fetch immediately

Beat waits for the next schedule boundary. If work still does not run, check Beat, Dispatcher, and Data Ingestor logs.

Read scheduler and ingestion logs 
docker compose --env-file .env -f infrastructure/compose.yml -f infrastructure/compose.release.yml --profile beat logs --tail 100 beat dispatcher data-ingestor
A setup command failed

Stop the sequence at that command. Keep its error message. Fix the stated cause before continuing.

Do not delete PostgreSQL or Redis volumes as a troubleshooting shortcut. For existing database passwords, follow database maintenance.

Which Compose files belong together?

-f adds a Compose file. Compose reads files in the listed order and combines them into one setup.

Files under infrastructure/
Task Files
Local web compose.yml + compose.backend.yml + compose.local.yml
Workers compose.yml + compose.release.yml
Production web compose.yml + compose.backend.yml + compose.edge.yml + compose.bulletin.yml
Integration tests compose.integration.yml alone, with the fixed test project name.

Local web and workers share the infrastructure project. Their files select services; they do not create separate databases.

What does each Compose file do?
Compose files · infrastructure/
File Purpose
compose.yml PostgreSQL, Redis, shared network, and data volumes.
compose.local.yml Local ports, Bulletin source mounts, development images, and local initialization.
compose.backend.yml Backend service and its network.
compose.bulletin.yml Production Bulletin image.
compose.release.yml Workers and one-time initialization.
compose.edge.yml Traefik router and Cloudflare Tunnel connector.
compose.admin.yml Optional pgAdmin database browser.
compose.integration.yml Disposable database, Redis, and test runners.
compose.alert-testing.yml Private alert testing services.
compose.alert-verification.yml Controlled configuration check; combine only with the integration file.
compose.domain-cutover.yml Special override for the documented domain transition and recovery.
What do the command arguments mean?
Read a Compose command
Part Meaning
--env-file .env Read configuration values from this file.
-f path/to/file.yml Include this Compose file. Later files can replace or add settings.
up Create missing containers and apply configuration changes.
-d Keep containers running in the background.
--wait Wait for services to run or become healthy when health checks exist.
--no-deps Do not start the selected service’s dependencies.
--profile prediction Include optional services assigned to this profile.
bulletin Target the Compose service named bulletin.

Explicitly targeting a profiled service can activate it without a profile flag. A profile selects services; it does not replace readiness checks.

Build, start, restart, or stop?
Choose the command for your task
Command Use it when
docker compose … build You need a new image from source. It does not start containers.
docker compose … up -d --wait You need to start services or apply changed configuration.
docker start container-name An existing container is stopped and its saved configuration is still correct.
docker compose … restart service You need the same container to restart. It does not apply changed image or environment settings.
docker compose … stop service You want to stop selected services and keep their containers.
docker compose … down You intend to remove services in the selected setup. It can remove shared data containers.
docker compose … down -v You deliberately want to delete Docker volumes, including database data.

The … stands for the configuration options shown in task commands. Do not copy these table entries as commands.

How do Dockerfiles connect to the apps?
Dockerfiles · Build context is the repository root
Dockerfile Used by
workers/Dockerfile Workers and initialization containers.
workers/prediction-worker/Dockerfile Prediction Worker, with model dependencies.
apps/backend-api/Dockerfile Backend API.

Example: build only the local Bulletin development image. This does not start a container.

Dockerfile command example 
docker build -f apps/quakestrikeph-bulletin/Dockerfile --target development -t quakestrike-bulletin:local .
  • -f selects the Dockerfile.
  • --target development selects the development stage.
  • -t names and tags the image.
  • The final . gives Docker access to files in the repository root.

Compose selects the same files through build.context: .., build.dockerfile, and build.target: development. Docker’s build -f selects a Dockerfile; Compose’s -f selects a YAML file.

The root .dockerignore excludes private settings, model files, and other files from the build. Release workers use tested images built by the repository’s image scripts.

Where do data and local changes stay?
Storage and mounts
Item What happens
PostgreSQL and Redis volumes Data stays when containers stop or are removed. Removing volumes deletes their data.
Bulletin source mount The container uses source files from your checkout. Saving a file updates the development app.
Bulletin dependency volume Keeps installed packages separate from source files. Refresh it after a lockfile change.
Model mount Workers read approved model files without changing them.
Bootstrap snapshots Workers receive read-only access. The initialization container can write readiness evidence.

Inside a container, localhost means that container. Apps use names such as postgres:5432 across shared networks. Your browser uses published local ports.

PostgreSQL and Redis have no host ports here. The public Bulletin container does not connect directly to either data service.

How production requests reach Backend

Traefik sends /api/v1/ to Backend port 3000. Other page requests go to Bulletin port 4321.

Standard production Bulletin server requests use the public domain and return through the edge. Local development sets API_TARGET to http://backend-api:3000. The documented domain-transition override also uses that internal address.

Production adds no public application ports on the host. Keep private tools outside public routes.

Run isolated integration tests

Use these on your development computer. The test database is disposable and separate from application data.

Run these three commands separately 
docker compose -p quakestrike-data-ingestion-test -f infrastructure/compose.integration.yml up -d --wait postgres-test redis-test
docker compose -p quakestrike-data-ingestion-test -f infrastructure/compose.integration.yml run --build --rm test-runner pytest --config-file workers/pyproject.toml workers/tests/integration
docker compose -p quakestrike-data-ingestion-test -f infrastructure/compose.integration.yml down -v

Check that pytest reports integration tests ran. Keep the exact project name. Never point TEST_DATABASE_URL at a development database.
